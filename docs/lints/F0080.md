## Why

A pin that two independent pieces of code can both claim (a diagnostic/test API meant for bring-up, and the driver task that normally owns that pin in production) will have whichever one wrote last win, silently, with no indication to either side that the other also has an opinion about that pin. The failure mode is specific to whichever two features happen to collide, and looks like an intermittent hardware fault rather than two owners stepping on each other.

## Example

Usb_io_fw's pin-diagnostic feature (`IF-16`) could still take GPIO8/GPIO9 as generic diagnostic points (`b200_board::pin_diag::MCU_PINS`, every pin `BoardState::available` lists) even though the I2C master task owns those same two pins whenever it's running; a `diag.pins` request could put them under SIO control out from under a live I2C transaction, and the I2C task would only reclaim them on its own next configure — bus recovers, but by luck of timing, not by design.

## How to fix

Track pin ownership centrally (one registry that every feature checks before taking a pin) and refuse a request for a pin another feature currently owns, with an error the host can see, instead of letting the last writer win.

## How it is checked

Check: src hard — proving two independent code paths can reach the same pin concurrently needs the full firmware model (every task, every API handler, what each one can touch), not a local pattern.

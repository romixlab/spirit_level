# G0001 core-crate-deps { #G0001 }

<a id="core-crate-deps"></a>

**Rule:** A _core crate depends only on other _core crates, the allowed layers and listed vocabulary crates.

## Parameters

| Name | Type | Default | Meaning |
|---|---|---|---|
| `suffix` | string | `"_core"` | the name suffix of type-only crates |
| `layers` | list of strings | `[]` | map layers a _core crate may depend on besides other _core crates |
| `vocabulary` | list of strings | `["serde", "serde_derive", "thiserror"]` | third-party crates a _core crate may use |

## Why

A `_core` crate holds the types others share: ids, data, errors, the vocabulary of a domain. To stay usable by a CLI, a server, a test or a wasm build it must not drag anything in: it depends only on other `_core` crates, on the layers named in `layers`, and on a short list of vocabulary crates (`serde`, `thiserror`).

## How to fix

Move what needs the dependency into the crate above the `_core` crate, or, when the dependency really is part of the types (a units crate, say), list it in `vocabulary` with an override reason.

## Configure

```toml
[lints.core-crate-deps]
level = "deny"
suffix = "_core"
layers = []
vocabulary = ["serde", "serde_derive", "thiserror"]
reason = "why this project wants it at this level"
```

Allow one finding in the code with `// spirit-level: allow(core-crate-deps) <reason>` ([waivers](../waivers.md)); the code works there too, as in `[lints.G0001]`.

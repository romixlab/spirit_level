## Why

The startup code's RAM-zeroing range (from `init_ram.rs`, per `memory-layout.md`'s "every other RAM bank gets a `NOLOAD` section ... and zeroes it at boot") overlapping `.uninit` — the section that holds the crash record or handoff data across a reset.

`.uninit` exists specifically to survive a reset unzeroed; if the generic RAM-zero loop's address range includes it by accident, the crash record from the fault that just happened is wiped before the next boot can read and report it.

## Example

Template 0.4: a bank-zeroing range computed from the RAM map's new layout started overlapping `bedrock_crash`'s `.uninit` section in usb_io_fw's `init_ram.rs` until the ranges were split apart explicitly.

## How to fix

Exclude `.uninit`'s range from any generic RAM-zero loop; it's zeroed only by an explicit factory-reset path, never at every boot.

## How it is checked

`elf mid`: read both the zeroing loop's address range (from the compiled `init_ram.rs`) and `.uninit`'s linked address range, and check they don't intersect.

## Source
